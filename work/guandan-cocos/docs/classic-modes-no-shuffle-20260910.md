# 经典场三模式与不洗牌发牌

## 产品约定

保留大厅“经典掼蛋”入口及既有四档底分，进入后只显示以下三项，移除团团转、升级80分及未开放占位。

| 模式 | 级牌与终局 | 发牌 |
| --- | --- | --- |
| 经典 | 随机 2～A，只打一副，不进贡 | 原有随机发牌 |
| 不洗牌 | 随机 2～A，只打一副，不进贡 | 单局多炸、组合更集中 |
| 连打过 A | 从 2 升级，进贡还贡，实际通过 A 关才结束 | 原有随机发牌 |

用户已确认“不洗牌”为单局多炸，**不是首局洗牌、后续复用收牌顺序**。好友房基础规则增加“发牌方式：随机发牌／不洗牌”；定局、传统升级、转蛋、复式均适用，但不改变各自局数、计分或换队规则。四档底分分别为 50、300、2000、10000。

## 实现边界

- `shared-core/src/lib/classicModes.ts` 是三模式及十二个模式×底分队列的共同来源；客户端选场、平台接纳与服务端开局使用同一契约。经典沿用 `classic_*`，另外使用 `no-shuffle_*` 和 `consecutive_*`。不同模式不混排，机器人补位、底分预留和终局结算沿用同一套服务。
- `shared-core/src/lib/dealing.ts` 独立负责发牌；`engine.ts` 不内嵌新算法。普通随机发牌在相同随机序列下保持原结果。
- 多炸算法从完整 108 张牌中随机抽取六种普通点数，各保留 4～6 张为牌包；其余为散牌。牌包与散牌随机排列、切牌后按 27 张分段，随机对应到四个座位。切口允许拆开牌包，所以不保证任何一手必有炸弹。大小王不做点数聚集，不指定受益玩家。
- 不使用用户身份、机器人标记、积分或牌力操纵发牌。随机源由服务端提供，不允许客户端提交牌堆；非法随机数和非法发牌模式直接拒绝。
- `dealMode` 进入共享规则校验、严格服务端白名单、签名房间设置和持久快照。开局、下一局调用同一发牌器。复式只发一次、再复制到两桌，绝不分别随机。
- 仅 `independent` 匹配打一副结束；`upgrade` 匹配不受好友房默认四局限制，保留正常准备、贡还与过 A 结算链。

## 本地验证

- 核心 19 个测试文件、133 项测试通过。涵盖所有级牌的牌数、唯一性、级牌/红心配标记、可复现随机源、原随机发牌兼容、模式映射及无效设置拒绝。
- 固定种子各 3,000 次、打 7：随机发牌每桌天然四张及以上炸弹平均 **5.5037** 组；不洗牌 **9.1013** 组。不计红心配拼出的炸弹或同花顺。后者四席平均分别为 **2.2687、2.2687、2.2773、2.2867** 组。此项是分布回归检查，不是胜率结论或严格公平性证明。
- 客户端全量回归通过；新增三尺寸菜单边界和十二种选场动作测试。实际 Cocos Web Canvas 在 874×402 视口点击三模式、好友房“不洗牌”和玩法规则，截图检查通过。沿用原素材和小圆角；收紧三项菜单，去掉遮挡第一项的重复标题。
- 服务端覆盖新模式签名票据、队列隔离、机器人补位、底分规则、连打过 A 超过 32 局不被截断、好友房下一局及 JSON 恢复仍使用不洗牌、复式双桌两局同牌、实际 WebSocket 开房/重连。
- Web 和微信本地包已构建；微信配置、分包、退役资源与模拟启动/恢复核验通过。模拟核验不能代替微信真机体验。

## 发布和验收

实现完成时仅通过本地验证；实际发布状态以本次发布回执为准，小游戏上传单独进行。**先发布含新队列及 `dealMode` 校验的服务端，再发布新客户端**，避免旧服务报“不支持字段”或“不支持队列”。既有已开始牌局不迁移规则。

服务端部署脚本 `ops/guangzhou/activate-server-variants.sh` 默认保留旧网页；显式传入 `--with-web` 时允许归档包含经过正式配置核验的 `web/`，与服务端一起切换并保留上一完整版本。部署前检查连接及活跃牌局，停服后备份数据；不替换凭据。
