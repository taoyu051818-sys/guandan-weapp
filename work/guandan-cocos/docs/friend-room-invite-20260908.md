# 好友房邀请与等待页：2026-09-08

## 本轮已实现

- 删除等待页右上角“复制完整邀请口令”及 Flow 的剪贴板分享方法。
- 中央操作行按实际按钮数量排列：邀请好友绿色、准备黄色；取消准备保持弱化，房主满足开局条件后出现开始游戏。
- 微信 `shareAppMessage` 使用 `friendRoom` / `friendInvite` 查询参数发送邀请卡片。分享参数不包含用户登录凭据、入桌票据或重连 token。
- `getLaunchOptionsSync` 处理冷启动；`onShow` 处理从后台打开邀请；销毁时解绑监听。
- 大厅就绪前保留邀请；启动中的旧牌局恢复查询结束前不抢占流程。已有房间/牌局时不自动退出，不覆盖当前席位。
- 通过既有平台好友房 join 接口校验邀请、事务预留席位。保留既有从 p2、p3、p4 顺序选择空位的逻辑；客户端不指定或伪造入座结果。
- 成功加入的玩家保留经平台验证的邀请，支持继续邀请。恢复接口未提供邀请数据时明确提示不可分享，不拼造邀请码。
- 本地允许机器人房的加号命中区域独立于整张席位卡，按下反馈带动加号本身；未绕过正式票据房的机器人限制。
- 顶部席位下移，避免真正加入的头像盖住规则摘要。沿用现有美术、按压反馈和小圆角，不新增动效。

## 尚未完成：不能当作已交付

1. **正式微信好友房加机器人**。牌局服 `weapp-lobby-command-handler.js` 当前拒绝票据房 addBot；平台 `friend-room-service.js` 独立管理预留席位。需要同时预留机器人席位，防止平台给真人发出同位置的有效票据；还要更新开局确认、机器人身份、结算、恢复及移除流程。
2. **坐下换座**。当前未新增可点击的假按钮。房主权限、首次入桌、席位身份和恢复票据绑定 p1/p2/p3/p4。需要服务端原子换座协议、明确的房主身份字段、旧票据失效策略及全员席位同步，不能只交换前端头像。
3. **真机卡片验收**。本地回归使用 wx API 测试替身，浏览器仅检查布局，不证明微信已发出消息、审核通过或另一手机已加入。

## 后续服务端工作边界

- 将房主身份与物理座位拆开；换座只允许未开局且未准备的玩家进入真正空位；房间开局确认期间禁止修改。
- 平台席位事务与牌局服席位同步必须有请求幂等标识、版本检查及失败恢复；不能绕过签名与票据验证。
- 机器人占位与真人 HTTP 预留竞争时只能一个成功；机器人不冒用真人账户，不产生真人钱包奖励。
- 四端必须同时看到新座位，恢复到新的座位；换座不得丢失退出/解散/房主权限，队友对应关系必须跟随座位正确变化。
- 覆盖并发邀请、机器人占位、换座竞争、重复命令、准备与开局竞态、持久化失败、断线与进程恢复。

## 验证

- Cocos `npm test`、TypeScript、架构检查；邀请模块测试涵盖冷/热启动、参数格式、重复激活、恢复等待、分享参数无用户票据、API 不可用、解绑和销毁。
- 等待页测试覆盖单按钮/两按钮/三按钮的居中、同列 Y 坐标、按钮间距与颜色；874×402 查看实际 Cocos 渲染。
- 平台 `friend-room-service.test.mjs` 验证现有邀请与席位逻辑。
- 独立离线预览：`http://localhost:18741/friend-room-invite-20260908/`。固定假房号只用于渲染，无平台/牌局网络连接；“准备”不是可联机验证入口。
- 微信实测：手机 A 创建房间→邀请手机 B；B 完全关闭小游戏后点击卡片、后台运行时点击卡片各一次；重复点击不能占两席。取消分享不显示“发送成功”。过期/已满房间须有明确错误；已有牌局时不能被邀请强行切走。
