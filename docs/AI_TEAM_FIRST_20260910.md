# 托管与机器人：队伍头游优先策略

2026-09-10，策略版本 `team-first-v1`。本次为源码和本地测试交付，没有部署线上服务，也没有上传微信包。

## 生效范围与目标

提示、四人经典／转蛋／赛事中的机器人、玩家托管，以及八人复式房的机器人和托管，全部使用唯一的最高档团队决策。服务端通过 `createRoomBotPolicy` 接入；复式每桌独立保存 AI checkpoint，不读取另一桌的同牌信息。提示调用同一策略，但保留用户锁牌限制，并即时显示，不添加模拟思考等待。

第一目标是本队有人先出完，不是机器人自己多出几张牌。合法性始终由原有规则引擎校验；本轮同时替换自动出牌延迟、统一提示排序，未改音效和牌桌布局。

## 决策顺序

| 情况 | 策略 |
| --- | --- |
| 当前一手能出完 | 立即出完；允许用炸弹，也允许接过队友的牌 |
| 队友控制牌权 | 通常让牌，保留队友领先机会 |
| 让牌可能丢掉头游 | 完整度足够的公开信息表明一张牌的对手极可能先走、自己能安全封住时，允许保护性接管；不会凭不完整记牌贸然抢队友 |
| 自己满手首次领出 | 混合手牌优先普通牌，不用炸弹开路；删除原来“对手剩五张就强制偏炸”等策略 |
| 对手只剩一／两张 | 领出时尽量避开对手恰好能一次出完的张数；跟牌时提高封堵和控制牌权的权重 |
| 队友进入十张以内 | 推断队友可能持有的牌型，评价递牌成功和途中被截断的风险；队友剩一张时倾向低单张 |
| 对手进入十张以内 | 加强其接牌／一手出完风险评估；按实际出牌顺序区分下一家、队友前后的威胁 |
| 普通中盘 | 比较出完剩余手牌所需的手数、单张尾牌、拆炸／拆组合成本与保留牌权 |

规则优先级先筛选，随后才按评分产生概率。只在同一优先级且评分接近的候选中选择；一般分差最多 12，紧急场景最多 3。不存在全局随机抖动把明显较差或低优先级的出法选出来。

## 按自己的牌力调整打法

结合整手预计出牌次数、散单数量、炸弹／同花顺、大小王、自然高级牌和红心配评估牌力，不按炸弹数量直接决定先炸。重复的同点数炸弹候选不会重复计算控制牌。

| 牌力／局面 | 战术倾向 |
| --- | --- |
| 结构紧凑、控制牌足够 | 争取主动，兼顾剩余路线和收回牌权 |
| 散牌多、控制牌少，队友进入十张以内 | 更重视给队友递牌、保留有用组合 |
| 预计只剩两手以内、有控制或队友尚未进入收尾 | 提高自己收尾及连续掌握牌权的权重 |
| 普通牌力 | 平衡整手出完次数、散牌和拆牌成本 |

这些是最高档内的战术区别，不是低档策略。能直接出完、保护队友与拦截对手的规则优先级仍高于牌力评分。决策记录包含牌力等级、采用的计划及控制牌估值，可用于复盘。

## 自动出牌时间

- 实测本次策略计算耗时，乘以 50，截取到 **500～3,000 ms**。
- 独立抽取一次随机数，**10% 概率将该次等待扩大为三倍**，即 1,500～9,000 ms；它不改变洗牌或选牌的随机状态。
- 从开始计算时计时，计算时间包含在总等待内，不再额外叠加；临近服务端回合截止时，以截止时间为上限。极端计算负载本身不能由定时器限时保证。
- 同一回合状态只计算一次，连同所选牌、计划出牌时间一起持久化。重试、重连、服务重启不重新抽延迟；状态变化或当前玩家取消托管则废弃该计划。
- 四人房与八人双桌房使用同一时间模块。提示即时返回；贡还贡等非出牌的自动动作使用零决策耗时的下限等待，不套用旧延迟策略。
- 删除旧开局延迟、特殊牌延迟与 `BOT_ACTION_DELAY_MS`／`TRUSTEE_ACTION_DELAY_MS` 配置。房间“托管”选项改为**开启／关闭**，沿用现有布局；为兼容旧房间，协议的 `trusteeSeconds` 非零值仅代表开启，不再表示 15／30／60 秒的自动动作间隔。

尚未进入托管的真人首次超时处理仍遵循原超时规则；进入托管后的出牌全部走最高档策略。

## 公开信息推断

- 只使用自己的牌、每家余牌数／队伍／顺序、完整的公开出牌与让牌记录。
- 服务端入口将其他玩家的手牌替换成只有长度的空数组；测试用代理对象禁止读取其他任何手牌属性。
- 从 108 张牌减去己方手牌及已经打出的牌，按花色与点数计数；当前有效出牌在历史里重复出现时不重复扣除。
- 联合抽样按各家余牌数无放回分配，避免同一张未知牌同时被分给多人。普通阶段 12 份样本，有其他玩家余牌不超过十张时 32 份。
- 让牌只是软证据：敌方能接却没接的样本降低权重，但不会认定“不要就一定没有”；给队友让牌几乎不降低权重。评估过去的让牌时，会把该玩家后来已打出的牌加回其当时的可能手牌。
- 自然级牌不能参与连续牌型，红心配不能模拟大小王，同花顺和四王强度遵循现有规则。
- 某家已经可能先出完时，不再把后面座位的接牌机会当作同一头游事件，避免座位顺序误判。

这些是启发式概率，不是读取真实暗牌，也不是已经训练或校准的真人胜率模型。有限抽样保留不确定性；只有公开牌池排除的可能才直接置零。不完整历史会降低记牌完整度。

## 整手规划与性能边界

原来的候选只按“牌型／点数／张数”合并，可能漏掉同点数但花色不同的出法。新增结构候选保留花色和红心配用法，仅合并可互换的同花色同点数副本，避免为出一张牌无意拆掉后续顺子。

规划使用按牌面数量归一化的状态和有界搜索：十张以内最多 1,600 个搜索节点，其他阶段最多 350 个；分支分别最多 32／12。预算耗尽返回合法的贪心分组估计，不把它宣称为最优解或必胜路径。小手牌测试与穷举分组对照。

结构候选缓存最多 12 手牌状态；牌型解析、概率查询和贪心尾牌计算复用结果。候选枚举本身仍受复杂红心配组合影响，因此不能把搜索节点预算理解成毫秒级硬实时保证。

## 记录、恢复与模块边界

每次决策保存原因、优先级、选择的牌、预计手数、公开信息完整度、各家牌型概率以及最多六个候选评分与实际选择概率。候选记录包含已选项；如果实际接近候选超过六个，展示项的概率之和可能小于一。

`getLastDecisionTrace().team` 返回隔离副本。最近八次记录保存在 `AIEngineCheckpoint.teamDecisions`，随现有房间持久化／恢复流程保存；换局清理，不新增全局玩家画像或无限增长的日志。记录只在服务端内部，不下发玩家视图。新 checkpoint 为 v2；旧版 v1 可迁移，保留随机状态和已有决策记录，丢弃退役的低档调参及旧记牌字段。恢复后只运行最高档。

新职责位于 `shared-core/src/ai/team/`：

- `policy.ts`：规则优先级、评分和概率选牌。
- `holdingShapes.ts`：可能持牌的牌型能力摘要。
- `belief.ts`：公开牌池、让牌证据、联合抽样。
- `tableOutlook.ts`：座位顺序与头游竞争。
- `handRoute.ts`：整手分组与剩余手数。
- `handStrength.ts`：自有手牌强弱和战术权重。
- `journal.ts`、`types.ts`：诊断记录及契约。

删除旧低档策略、难度配置、旧大师强制策略、旧搜索和后备选牌分支，同时删除 Cocos 对应生成代码与孤立资源元信息；可从修改前的 Git 提交恢复。对外类型只接受 `master`；旧 JS 调用即使传入退役档位也归一为最高档，不再存在可切换的低档实现。Cocos 的 `core/generated` 只从共享源码同步，不直接修改。

## 验证与复现

新测试覆盖候选结构、花色／红心配规则一致性、小手牌穷举、首手保炸、强弱牌策略、队友配合、上下家余牌压力、暗牌不可读、概率日志隔离、旧 checkpoint 兼容和复式恢复。提示与自动决策在同观察、同随机种子、无锁牌限制时首选一致；锁牌时不会推荐拆开已锁组。延迟测试使用注入的时钟与随机数验证区间、10% 阈值、三倍等待、截止时间、取消与恢复，避免靠真实长等待碰运气。另运行共享核心、客户端、平台及牌局服全套回归。

基线为本次修改前 `b74df82`（与合并后的 `origin/main` 树相同）的共享核心构建。固定同一副牌，交换新旧策略所在队伍，以首次出完的队伍为指标，不用机器人自己出掉的牌数衡量强弱。

```sh
node scripts/benchmark-team-ai.mjs /path/to/baseline/dist 32 2000
```

此命令要求先构建当前共享核心。它不访问线上服务，逐手校验合法性，记录头游、耗时及开局炸弹。样本结果仅用于版本比较，不代表真人局胜率。客户端回归与会重建共享 `dist` 的服务端回归应顺序执行。

本次最终固定样本（32 副牌，各交换队伍一次，共 64 局）：

| 指标 | 结果 |
| --- | ---: |
| 新策略队伍拿到头游 | 45 / 64（70.31%） |
| 旧策略队伍拿到头游 | 19 / 64 |
| 检查的出牌／让牌动作 | 5,125 |
| 非法动作 | 0 |
| 新策略开局炸弹 | 0 |
| 新策略决策次数 | 2,569 |
| 本机耗时中位数／P95 | 2.088 ms / 19.655 ms |
| 本机最慢复杂手牌 | 769.453 ms |

耗时受本机负载影响，不等于线上服务器性能承诺。复杂双红心配仍可能明显慢于常规决策，应在上线后继续观察并发牌桌负载。开局样本中旧策略也没有出炸弹，因此“修复不合理开局炸弹”主要由专门的混合满手牌场景测试验证，而不是用这组对比数据证明。

共享核心 116 项测试通过；客户端完整回归、平台／牌局服完整回归通过。核心类型检查、Cocos 运行时与测试类型检查、同步／架构／健康检查，以及机器人／托管／复式定向回归通过。真机测试未执行，未构建新的微信上传包。

## 真机验收流程

| 步骤 | 操作／场景 | 通过标准 |
| --- | --- | --- |
| 1 | 服务端更新后，四人房加入机器人并开始 | 能正常发牌、轮转和完成结算 |
| 2 | 自己点击托管，观察几个回合，再取消托管 | 托管主动走合法策略，不是一律不要；取消后恢复手动 |
| 3 | 观察满手首次领出 | 有合理普通牌时不开场乱炸；不能以“任何情况都不许炸”验收 |
| 4 | 队友余牌进入十张以内／只剩一张 | 不随意顶队友，获得牌权后有递牌倾向 |
| 5 | 下家或上家余一／两张，自己有多种合法出法 | 不固定递送对手需要的张数；紧急时优先拦截 |
| 6 | 对手剩五张，自己有普通跟牌和炸弹 | 不因“五张”这个数字自动出炸弹 |
| 7 | 切后台、重连，继续托管到结算 | 牌局恢复正常，没有重复扣牌、乱序或非法出牌 |
| 8 | 八人复式房，两桌机器人／托管并行 | 两桌各自正常推进，不使用另一桌暗牌；局次同步和总分结算正常 |
| 9 | 有可出牌时点击提示并循环；再锁定组合后重复 | 推荐合法牌，不部分拆开锁牌；建议让牌时明确提示；不刻意等待 0.5～3 秒 |
| 10 | 多次观察普通机器人／托管回合，结合服务端计划记录 | 通常为计算耗时放大后的 0.5～3 秒，少量回合为三倍；统计样本不要求每十次恰好一次 |
| 11 | 自动出牌等待期间取消托管；两类房间都测试 | 不执行已取消的旧计划；不重复出牌、不重新随机拖延 |
| 12 | 创建房间开关托管；恢复旧非零托管设置的房间 | 仅展示开启／关闭，开启后采用统一延迟，不沿用旧 15／30／60 秒间隔 |

如发现异常，保留房间号、局次和大致出牌顺序；服务端的公开历史和决策记录用于复盘。此表是待上线后的验收步骤，不表示已经完成手机实测。
