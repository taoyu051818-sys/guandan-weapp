# 八人双桌复式（2026-09-09）

## 实现范围

- 好友房选择“复式”可以创建八席房间。准备页按 A/B 两行、红/蓝两侧组织；A 桌南北为红、东西为蓝，B 桌相反。使用现有小圆角、头像资源和绿色/黄色按钮，不复制参考图的商用美术。
- 房主可点加号添加陪练、移除陪练或补齐机器人；所有玩家可先站起、再坐入空位。八席到齐且全部准备后由房主开始。
- 邀请复用原有微信分享卡片；六位房间号复用原有加入弹窗。没有增加复制粘贴口令页面。
- 同一局只发牌一次，再复制到两张子桌：对应方位牌序、级牌、首次出牌方位一致。默认固定打 2；随机级牌也是两桌共享一次随机结果。不升级、不进贡。
- A/B 桌独立出牌、计时及托管；两桌均结束后累计红蓝队积分。每桌头二/头三/头末分别为胜方 3/2/1 分、负方 0 分。两桌、八席的准备屏障满足后才进入下一局。
- 先结束的参赛者可只读查看另一桌，再返回本桌准备。比赛中不能换座或操作另一桌手牌。外部观战沿用房间实时/延迟设置；延迟画面不提前携带当前结果。
- 全场结算按红蓝队而不是子桌本地 p1/p2 的队伍解释胜负。重连恢复全局席位、当前观看桌、两桌状态与累计积分。

## 模块边界

- `server/duplicate-room-runtime.js`：串行事务、存储、连接、时钟、签名事件重试。
- `duplicate-room-model.js`：一次发牌/双桌复制、单桌出牌、跨桌积分与局间屏障。
- `duplicate-room-admission.js`：八席签名票据、恢复凭证、身份和容量校验。
- `duplicate-room-actions.js`：准备、换座、陪练、观战和快捷语权限。
- `duplicate-room-projection.js`：私有手牌裁剪及延迟观战投影。
- 平台 `friend-room-service` 支持八席预约；`duplicate-room-roster` 在签名开局事务中锁定八个参赛身份。
- Cocos `DuplicateRoomWaitingView`、`DuplicateTableStatusView`、`DuplicateTablePresentation`、`DuplicateRoomModel` 分别负责准备页、只读跨桌入口、红蓝结果和网络模型。
- 四人引擎及普通房仍保持四个本地 PlayerId。全局 p5～p8 只存在于复式协调器和签名平台席位中，客户端子桌仍使用 p1～p4。

## 核验

- 真实八条 WebSocket 连接 + 平台服务：八席顺序预约、满房拒绝、签名名单、对应手牌相同、对手手牌隐藏、恢复 B 桌身份、最终结果幂等。
- 两局完整引擎回归：换座、共享随机级牌/首出方位、先结束桌观战、禁止跨桌操作、双桌屏障、积分、请求去重、进程重建恢复、落盘失败回滚、延迟结果隐藏。
- 原有平台和游戏服回归通过；共享核心 16 套 82 项通过；客户端 77 项检查通过（新增模块的显式测试依赖同步更新）。
- Cocos 实际 874 × 402 横屏渲染复查：从初稿中分离空座操作与底部准备区，添加头像与姓名层级。UI/UX 技能用于检查按钮间距、红蓝文字标识及安全区。
- TypeScript、架构 58 个大小预算、健康清单通过；未增大现有类的大小预算。
- 微信正式包已构建并核验：主包 3,099,760 字节，资源分包 13,433,169 字节，总计 16,532,929 字节；包含严格域名检查及模拟启动/恢复检查，不代表真机登录验收。

## 发布和真机边界

未部署线上服务、未上传微信、未提交 Git。必须先同步部署共享核心、平台服务与游戏服，再发布同版本 Cocos 包；旧服务不理解 duplicate 八席协议。

持久化文件为 `WEAPP_ROOM_STATE_FILE` 后加 `.duplicate`，应与原牌局文件一起备份。票据、比分回调沿用现有签名密钥和 HTTPS/WSS 域名；本机测试地址仅在测试进程使用，不写入正式客户端配置。

最终还需微信真机多人验收：创建复式 → 微信卡片邀请 → 分别进入 A/B 桌 → 双桌各打完一局 → 跨桌只读观看 → 返回准备 → 切后台/重新进入 → 全场结算。自动化八连接通过不等于八台手机验收。
